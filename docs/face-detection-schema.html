Facewright·internal reference·schema & matching

How a photo becomes a face, and a face becomes a person

What actually happens in the database between an uploaded photo and a named person on Memories' People page — table by table, row by row.

00  —  the short version

Three tables carry the whole system. A Nextcloud file is linked to zero or more face detections (one row per face InsightFace found in that photo). A face detection is linked to zero or one cluster — a cluster being Facewright's notion of "a person." Detection and clustering are two separate passes, run at different times, connected only through the data they leave behind.

Nothing here is Facewright's own schema by choice — these are Recognize's tables. Facewright writes into them so Memories' existing People page can read them without knowing Facewright exists.

01  —  the three tables

What's actually on disk

One table per concept. The fourth table you'll see mentioned elsewhere in this project, facewright_processed, is not part of this — it only tracks which files have been attempted, for idempotency. It has no opinion about faces or people.

oc_recognize_face_detections one row per face
  • idprimary key
  • user_idwhose library this photo belongs to — detections are always scoped to one user
  • file_idNextcloud's internal, rename-proof file id — the only link back to an actual photo
  • x, y, width, heightthe face's bounding box, as fractions of the image (0.0–1.0), not pixels
  • face_vectorthe face embedding — a JSON array of floats. 512 numbers if Facewright wrote it, 128 if Recognize's old classifier did
  • cluster_idwhich person this face belongs to — NULL until a clustering pass decides
oc_recognize_face_clusters one row per person
  • idprimary key — this is what cluster_id above points to
  • user_idclusters are private: "Anna" in your library and "Anna" in someone else's are unrelated rows
  • titlethe person's name — starts empty, set later by renaming them in Memories
oc_facewright_processed bookkeeping only
  • user_id, file_idunique together — "has this file already been attempted"
  • processed_at, faces_foundeven 0 counts — this is what stops zero-face photos from being retried forever

02  —  the shape of the data

Files, faces, and people are a chain, not a lookup table

There's no table that maps a file directly to a person. You get there by walking through the detections: file → its faces → each face's cluster. That indirection is what lets one photo hold several different people, and one person show up across hundreds of unrelated photos — worked below with three real-shaped rows, not placeholders.

one group photo (8841) holds two different people; one person (Anna) recurs across two unrelated photos; one face isn't confident enough to join a cluster yet

Read the arrows both directions and you get both of your original questions for free: files → faces is "what does this photo contain," and faces → clusters, walked backwards, is "which photos does this person appear in." Memories' People page does exactly that second walk — see §05.

03  —  detection

How a file gets its face rows

Detection is triggered four different ways — a new upload, the admin page's "Run now," the self-requeuing "Scan entire library," or occ facewright:detect by hand — but all four converge on the same steps:

  1. A trigger identifies a candidate as (user_id, file_id, path) and hands it to DetectionService.
  2. DetectionService calls the facewright ExApp's POST /detect, impersonating that user so the ExApp can read the file from their storage.
  3. Inside the ExApp, InsightFace (buffalo_l, CPU) returns a pixel bounding box, a 512-float normalized embedding, and a confidence score — per face found.
  4. The bridge converts each pixel bbox to a 0.0–1.0 fraction of the image, and INSERTs one row per face into recognize_face_detections. cluster_id is left NULL — nothing here decides who anyone is.
  5. Whether one face was found or none, facewright_processed gets a row, so this file won't be attempted again automatically.

one pass, one file, zero decisions about identity

04  —  clustering

How faces become a person

Clustering is a separate pass, run later, by hand or from the admin page — never automatically after detection. It only ever looks at one user's own 512-dimension rows (Recognize's old 128-dimension embeddings are a different, incompatible space and are filtered out before any comparison happens), and only at rows where cluster_id IS NULL.

For each unclustered face, it measures cosine distance to every other loaded face of that same user — 0 meaning identical, larger meaning less alike. If at least min-faces (default 3, including the face itself) fall within max-distance (default 0.5), it joins whichever of those matches already has a cluster, or starts a new one if none does. Otherwise it's left NULL — not wrong, just not enough evidence yet, and eligible again next run.

why the 512 / 128 split matters

This instance still has roughly 8,300 old 128-dimension rows from Recognize's original face-api.js classifier, sitting in the same table as Facewright's own 512-dimension InsightFace rows. Comparing across that boundary isn't just inaccurate — the vectors aren't in the same space at all, so a "distance" between them is meaningless. Every place that reads embeddings for clustering filters to exactly 512 first.

05  —  reading it back

How Memories turns a cluster into "Anna's photos"

There's no code in Facewright for this — it's the same walk from §02, run backwards, by Recognize and Memories' own existing machinery:

  • Memories' People page lists recognize_face_clusters rows for the current user, showing title where one's been set.
  • Opening a person queries recognize_face_detections WHERE cluster_id = <that id>, then follows each row's file_id back to the actual photo to render a thumbnail, cropped using that row's x, y, width, height.
  • Naming a person is a rename on a virtual WebDAV folder Recognize exposes per cluster — which, under the hood, is just an UPDATE … SET title = … WHERE id = … against the same row.

Reflects recognize_face_detections, recognize_face_clusters, and facewright_processed as written by facewright_bridge — see the repo's CLAUDE.md for the full build history behind each piece.
